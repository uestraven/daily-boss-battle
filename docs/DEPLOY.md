# Deploying to Cloudflare Pages

The game is a static build with no server. Everything it needs — the verified encounter
pool, sprites, audio — ships in the bundle, so there is nothing to run and nothing to
scale.

## One-time setup

In the Cloudflare dashboard: **Workers & Pages → Create → Pages → Connect to Git**, point
it at `uestraven/daily-boss-battle`, then set:

| Setting | Value |
| --- | --- |
| Framework preset | **None** |
| Build command | `npm run web:build` |
| Build output directory | `web-dist` |
| Root directory | *(leave blank — the repo root)* |
| Production branch | `main` |

Node version comes from `.node-version` (22). Cloudflare runs `npm ci` automatically
because `package-lock.json` is committed, and installs devDependencies, which the build
needs for `tsc` and `vite`.

That is the whole configuration. Every push to `main` deploys; every pull request gets a
preview URL.

### Optional: email reminders

The signup form only renders when an endpoint is configured, so without this it is simply
absent rather than silently discarding addresses. Add an environment variable under
**Settings → Environment variables**, for production and preview:

```
VITE_REMINDER_ENDPOINT = https://your-form-provider.example/f/abc123
```

Buttondown and Formspree both accept a plain form POST, which is what the component sends.
It is a build-time variable, so changing it needs a redeploy.

## Deploying from a terminal

`wrangler.toml` keeps the output directory in version control and makes direct uploads
work, which is useful for testing a build without pushing:

```bash
npm run web:build
npx wrangler pages deploy web-dist
```

## What the config files do

- **`web/public/_headers`** — Vite copies this to the build root. Caching splits three
  ways: Vite's `/assets/*` are content-hashed so they are immutable forever; files served
  from `public/` are *not* hashed, so they get a day of freshness plus a week of
  stale-while-revalidate, which is fast for repeat visitors while still letting an updated
  asset propagate; and `index.html` must revalidate or a deploy never reaches anyone. It
  also sets `nosniff`, a referrer policy, `X-Frame-Options` and a `Permissions-Policy`.
- **`.node-version`** — pins the build to Node 22, matching CI.
- **`wrangler.toml`** — names the project and the output directory.
- **`web/public/sw.js`** — the service worker (see below).

There is deliberately **no SPA fallback** (`/* /index.html 200`). The app has no
client-side routing, and a catch-all would return `index.html` with a 200 for a missing
asset, which would hide a genuinely missing sprite or sound behind a successful-looking
response. Unknown paths should 404.

## The service worker

`web/public/sw.js` is hand-written rather than generated by Workbox, so it is short enough
to read in full and has no build-step coupling. It earns two things: Chrome on Android only
offers **Install app** when a worker with a fetch handler is registered, and the game is
fully playable offline by design — the verified encounter pool is bundled into the
JavaScript and the engine never calls out — so caching the shell makes that real rather
than theoretical.

`web/src/register-sw.ts` registers it, on `load`, in production builds only. A failed
registration is logged and ignored; the game does not depend on it.

Caching is split by how the thing is named:

| Request | Strategy | Why |
| --- | --- | --- |
| Navigations / HTML | **network-first** | A deploy must always reach people. Falls back to cache offline. |
| `/assets/*` | **cache-first** | Content-hashed by Vite, so immutable by construction. |
| sprites, audio, icons, manifest | **stale-while-revalidate** | Unhashed, so served fast and refreshed in the background. |
| anything else, any cross-origin | **untouched** | The email endpoint is never intercepted. |

A service worker persists across visits, so a bad one keeps serving a broken app. Four
things make that recoverable:

- **HTML is never cache-first**, so a fix always lands.
- **No `skipWaiting`.** A new worker waits for existing tabs to close instead of taking
  over mid-session. That costs nothing: because HTML is network-first, a returning visitor
  already gets the new `index.html` and its new hashed bundles. Only the worker's own code
  lags one visit. The tradeoff is that an *updated sprite or sound* can show one visit
  late, since those are unhashed.
- **Only `basic` 200s are cached** — no opaque cross-origin responses, no `206` partials
  from a Range request, no errors stored as content.
- **`_headers` sends `Cache-Control: no-cache` for `/sw.js`.** This is the critical one: a
  worker cached by the browser cannot be replaced. `npm run pwa:check` asserts it.

To recover by hand: devtools → Application → Service workers → Unregister. Bumping
`VERSION` in `sw.js` drops every old cache on activation.

**What "offline" actually covers.** The precache holds only the shell — `index.html`, the
manifest, two icons. Everything else is cached on first use, deliberately: precaching every
sprite and the full battle theme would cost a first-time visitor megabytes of mobile data
they may never come back to spend. So a boss or sound you have already seen plays offline,
and one you have not degrades instead of breaking — `BattleStage` falls back to silhouettes
for a missing sheet and `playCues` skips a missing sample. The engine itself never needs the
network, so the battle always runs.

## Before the first production deploy

```bash
npm run verify       # tests, behaviour guard, verified pool freshness
npm run pwa:check    # manifest and icons
npm run audio:check  # which audio is present, and its size
npm run web:build    # the build Cloudflare will run
```

Then open the preview URL on a phone and check:

- the battle plays, and the theme starts on the first action
- **Add to Home Screen** on iOS shows the sword icon, not a screenshot of the page
- the result card's **Share image** opens the native share sheet with a PNG attached
- safe-area insets keep the UI clear of the system bars
- Chrome on Android offers **Install app** in the menu, and the installed app opens without
  browser chrome
- **offline play**: load the page once, then turn on airplane mode and reload — the battle
  should still start, with sprites and sound

The worker only runs over HTTPS or on `localhost`, so a Cloudflare preview URL or
`npm run web:preview` will exercise it, but an IP address on the local network will not.

## Known gaps at launch

- **No Content-Security-Policy.** Worth adding, but a wrong one is a blank page, so it
  should be set and verified against a preview deployment rather than guessed. The email
  endpoint needs to be allowed in `connect-src` if one is configured.
- **Results are per-browser and unverified.** There is no account and no server
  adjudication; the UI says so. See the technical plan for what a backend would add.
